# outbox-vs-dual-write

How many messages does a PostgreSQL-to-broker publishing strategy actually lose
when the broker is killed mid-load?

Two strategies, measured against the same failure injection:

- **dual write** — commit the order to Postgres, then publish to the broker
  synchronously in the write path. A publish that fails is dropped.
- **transactional outbox** — write the order and its event row in one
  transaction; a relay poller publishes unsent rows and marks them sent,
  retrying until the broker comes back.

A third arm, CDC via Debezium, was planned and **dropped** — see the ADR. It did
not fit the disk budget on this machine and no CDC number is reported anywhere.

Ground truth is the `orders` table. The consumer writes every id it receives to
a sink; reconciliation is a set difference, not an estimate:

```
lost  = written - received
dupes = received - distinct(received)
```

## Headline

See `results/SUMMARY.md` (regenerated by every run) and `WRITEUP.mdx`.

## Machine

Apple M1 Pro, 8 cores, 16 GB RAM, macOS (Darwin 25.6.0). Docker via OrbStack
29.4.0, Linux VM capped at 8 CPU / 8 GB RAM. The writer, relay, consumer and
reconciler all run on the host as one Go binary and reach the containers over
`localhost`. Go 1.26 (toolchain 1.27).

## Reproduce cold

```bash
git clone https://github.com/dhiazfathra/outbox-vs-dual-write
cd outbox-vs-dual-write
docker compose up -d
make bench
```

`make bench` is the one command. It takes the shared `/tmp/bench.lock` so only
one benchmark runs at a time on the machine, brings the stack up, waits for both
health checks, then runs every arm and writes `results/`.

Knobs: `N=50000 REPS=4 ./run-bench.sh`. Rep 1 of every arm is a warm-up and is
discarded by the aggregator.

Tear down with `make down` (`docker compose down -v`) — it removes the volumes,
which matters on a machine with little free disk.

## What each run does

1. Applies `schema.sql`, which drops and recreates `orders` and `outbox`.
2. Deletes and recreates the `orders` topic (1 partition, 1 replica) so every
   repetition starts from an empty log.
3. Starts a consumer that reads the topic from offset 0 with no consumer group,
   so a broker restart cannot cost it committed offsets.
4. Runs 50,000 writes across 16 workers. Amounts come from a fixed seed
   (`rand.NewSource(42)`), so every run writes byte-identical rows.
5. In the injection arms: when the write counter crosses 40% of `N`, a goroutine
   runs `docker kill ovd-redpanda`, waits 10 seconds, then `docker start`. The
   trigger is the write counter rather than the wall clock, so both strategies
   are hit at exactly the same point in the workload.
6. Waits for the consumer to go 15 seconds without a new record, then reconciles
   the sink against `orders` and writes a summary plus the gzipped raw per-record
   data to `results/`.

Each strategy also runs a **control** arm with no injection, so steady-state loss
and steady-state lag can be separated from failure-induced loss and lag.

## Layout

| path                 | what                                             |
| -------------------- | ------------------------------------------------ |
| `main.go`            | flags, run orchestration, injector               |
| `arms.go`            | the two strategies and the relay poller          |
| `consumer.go`        | sink consumer                                    |
| `report.go`          | reconciliation, percentiles, recovery time       |
| `cmd/aggregate`      | turns `results/*.json` into `results/SUMMARY.md` |
| `run-bench.sh`       | the harness, including the benchmark lock        |
| `results/`           | raw output of every run, committed               |
| `docs/adr/0001-*.md` | the decision and its consequences                |
